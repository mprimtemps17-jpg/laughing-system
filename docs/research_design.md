# 研究設計 v0.2 と、この環境の対応

出典：統合記録 第1版（2026-10-25）。ここでは環境のどこで何を実現しているかだけをまとめる。設計そのものは統合記録を正とする。

## 研究質問（v0.2）

同一の元情報を与えたとき、人物ごとの知識を明示的に整理してから判定する方法は、直接判定する方法より、人間の基準判定と一致するか。

最初の対象は、2人の予定調整会話での時間制約の反映。LLMは第三者の評価者として、Aの指定された1発言を判定する。

## 設計の各要素と実装

| 設計（統合記録） | 実装 |
|---|---|
| 配慮不足の操作的定義（4条件）と4ラベル（あり／なし／判定対象外／保留） | `configs/care/criteria_v0.2_time.md`。全条件の最終判定にそのまま渡す |
| A：直接判定（1回） | 条件 `A_direct` |
| B：知識整理→判定（2回）。第1段階に対象発言・正解を見せない。①制約 ②Aが知る内容と引用 ③Bだけが知る内容と引用 ④共有が確認できる内容 ⑤情報不足 | 条件 `B_knowledge`。`care/prompts.py` の `KNOWLEDGE_FIELDS`。整理表は修正せずに保存し、元の文脈と一緒に判定へ渡す |
| C：人物別にしない一般的な整理→判定（2回） | 条件 `C_general`。項目数（5）と字数上限（80字）をBにそろえた |
| 最終出力 `{"判定","根拠引用","短い理由"}` | `{"label","evidence","reason"}`（構造化出力でJSONを保証） |
| 各例・条件で履歴をリセットする | 各呼び出しは独立（過去の判定や同じ場面の別変種を含めない） |
| 条件の実行順は固定した交替順で、その順を保存 | `plan_jobs`：例ごとに A,B,C → B,C,A → … と交替。`order` を記録 |
| 実行日時・版・設定・生出力を残す | `results/<run>/`（`meta.yaml`、`config.yaml`、`criteria.md`、`data.jsonl`、`judgments.jsonl`） |
| 形式違反・通信エラーを隠さず記録 | `error` 欄。集計では正解に数えず件数を表示 |
| 予備6件（P1・P2×3変種） | `data/care/v0.2_pilot.jsonl`（split: pilot） |
| 評価用の別8場面×3変種＝24件（作成予定） | `configs/gen/time_eval_template.yaml` で候補を生成（split: eval）。予備と同じ活動は使わない |
| 予備と評価で同じ基本場面の言い換えをまたがせない | `scene_id` と `scene_signature`。`check_splits` が警告し、生成時は `avoid_scenes_in` で除外 |
| 本番では情報伝達の経路を読む必要のある例を入れる（Aの不在、Bの個別メモなど） | 生成の経路：既知＝直接／グループチャット／第三者経由、未知＝Bだけ／不在中／手帳 |
| 露骨な手掛かり語を使わない | 生成の自動点検（`gen/quality.py` の `CUE_WORDS`） |
| Bの反応を入力に入れない | 対象発言の後の発言を持たないデータ形式。生成プロンプトでも禁止 |
| 人間の独立判定（AI案・モデル回答を見ない） | `human export`：評価票に作成意図・場面ID・変種を含めない。提示順は乱数の種で決めて記録 |
| 一致率80%未満なら基準を再検討 | `human agreement` が表示 |
| 主指標・誤帰属・組全体の一貫性・対応する正誤の変化 | `care analyze`（`metrics.csv`、`paired_changes.csv`） |
| 誤りの分類 ①取り違え ②照合失敗 ③確認・変更の見落とし ④基準の曖昧さ | `errors_for_review.csv` の `error_category` 欄に人が記入 |
| APIがなくても進められる | `backend: manual`（プロンプトの書き出しと回答の取り込み） |

## v0.1 の素材の扱い

- `data/care/v0.1_dev.jsonl` に D01〜D20 を収録。ラベルは v0.1 の3分類（あり／なし／判断保留）のまま書き換えていない。
- 内容が重複する D09・D11・D13 は `notes` に記録。近い場面（P01/P05/P10、P02/P06/P09、P03/P07）は同じ `scene_id` にまとめた。
- v0.2 の4分類で使う場合は、「判断保留」の例を再点検してから変更し、履歴を残す。

## 今後の作業（統合記録 第4章）と、使うコマンド

| 順序 | 作業 | 使うもの |
|---|---|---|
| 1 | v0.2の定義と6例を本人が判定する | `human export data/care/v0.2_pilot.jsonl ...` |
| 2 | 協力者1人に独立判定を依頼する | 同上（seed を変えて別の票を作る）→ `human import` |
| 3 | 曖昧な例と定義を修正して固定する | `human agreement`、`configs/care/criteria_v0.2_time.md` を編集して版を上げる |
| 4 | 1モデルで6件の予備実験を行う | `care run configs/care/pilot_claude.yaml`（または `pilot_manual.yaml`） |
| 5 | 予備で使っていない8場面24件を作る | `gen run configs/gen/time_eval_template.yaml`（または LLM 生成）→ 人が読んで修正 → 人間判定を**モデル実行前に**確定 |
| 6 | 24件で条件をそろえて比較する | 評価用の設定（`data` を評価データに、`splits: [eval]`）で `care run` → `care analyze` |
| 7 | 一般整理のC条件を加えるか決める | `conditions` に `C_general` を追加 |
| 8 | 誤り分析とゼミ報告 | `errors_for_review.csv`、`report.md` |

## まだ決まっていないこと

- 使うモデル・API の有無・費用上限（設定ファイルの `model` で切り替えられる）
- 独立判定を頼める人
- 予定以外の場面へ広げるか（`criteria_v0.3_general_draft.md` と `mixed_template` は、その検討用の案）
